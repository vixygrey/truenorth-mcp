# v2.0.0

## Highlights

- Retires Jev and removes the `truenorth_guard_change` MCP tool. No replacement
  guard service or filename-policy system is introduced. MCP clients should
  rediscover the remaining tools after reconnecting.
- Removes `truenorth-mcp guard` (stdin), `truenorth-mcp guard --staged`,
  and `truenorth-mcp guard --range <range>`. The independent `guard-git`
  credential scanner and the runtime's filesystem/write boundaries remain in
  place.
- Removes the `jev-http` Cargo feature, the `jev_bench` and
  `jev_provider_smoke` binaries, and the Jev HTTP transport. Fresh scaffolds
  and package bootstraps no longer install `.kiro/hooks/jev-guard.json`.
- Supports managed workspace upgrades from bundle versions `1.0.2`, `1.0.4`,
  `1.0.5`, and `1.2.1`. Historical bundle manifests are preserved; the
  workspace and bundle schema numbers are unchanged.

## Migration

Install the 2.0.0 runtime and its matching package bundle. Commit or back up
the governed project and review any locally modified hooks or configuration.
From the project Git worktree, run:

```sh
truenorth-mcp upgrade --check --bundle-dir <new-package-bundle>
truenorth-mcp upgrade --bundle-dir <new-package-bundle>
truenorth-mcp --check-config --strict
```

The first command is read-only. Before apply, the Git worktree and index must
be clean and no other server may hold the writer lease. Apply removes a
verified unchanged, owned retired hook through the existing upgrade
transaction. A manifestless hook matching verified historical seed bytes and
mode can be adopted and removed. A modified, unowned, or unverifiable
`.kiro/hooks/jev-guard.json` is preserved and reported: its owner must disable
or remove it before using the new runtime. Other hook files and unrelated
settings are not deleted. Recheck the plan and resolve any reported conflicts,
rather than overwriting local changes.

Remove `features.jev`, top-level `jev`, and guard-only `protected_paths` from
the project's `.agent/config/rules.yml` without replacing unrelated settings.
These are now unknown configuration keys: non-strict inspection warns, and
strict inspection fails. Remove old client registrations or hooks that invoke
`truenorth_guard_change` or `truenorth-mcp guard`, then reconnect MCP clients.
Remove operator-supplied `TRUENORTH_JEV_ENDPOINT` and
`TRUENORTH_JEV_API_KEY` from obsolete runtime/client configuration. There is
no automatic Jev-report conversion; preserve any user telemetry.

Rollback requires restoring the prior matching runtime/package bundle and the
backed-up workspace, including any intentionally removed hook and
configuration, before reconnecting older clients. Do not downgrade merely to
bypass filesystem checks or reuse old provider credentials.

## Operator retirement checklist

- [ ] Confirm required CI status names and rulesets do not retain obsolete
      Jev-only checks; keep the independent credential scanner required.
- [ ] With operator authorization, stop pending Jev dispatches or deployments
      and prevent further provider execution. Do not run paid validation
      workflows.
- [ ] Inventory Jev-only Environment secrets and variables **by name only**,
      including `TRUENORTH_JEV_ENDPOINT`, `TRUENORTH_JEV_API_KEY`, and any
      separately configured Jev timeout, retry, or endpoint settings. Do not
      retrieve or log values. Ask the credential owner to revoke provider
      access, then remove Jev-only GitHub/client/operator settings. Delete a
      Jev-only Environment only after checking for unrelated consumers.
- [ ] Preserve historical workflow artifacts, source history, bundle
      manifests, and user telemetry. Removing a workflow or Environment does
      not prove provider-side credential revocation; record owner confirmation
      separately.
- [ ] Link and close superseded issue work only after the repository,
      workspace, CI, distribution, and operator criteria have evidence. Do not
      mark previous Jev production-readiness criteria as passed.

These operator steps require separate authorization and confirmation; this
release note does not assert that they have been completed.
